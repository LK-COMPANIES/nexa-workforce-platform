# Compliance Readiness — Nexa Workforce Solutions Ltd

**This is an engineering compliance-readiness matrix, not legal advice and not a certification.** It records what the platform's code and infrastructure actually do today, maps that to the legal/regulatory areas it touches, and is explicit about the difference between a technical control existing and a legal obligation being satisfied. Where a claim requires a lawyer's judgment rather than an engineer's, it is marked **Requires Legal Review**, not asserted as done.

Status vocabulary used throughout, per the Phase 5 brief:

| Status | Meaning |
|---|---|
| **Implemented** | The control exists in code/infrastructure today and is exercised by tests or direct inspection. |
| **Partially Implemented** | Part of the control exists; a real, named gap remains. |
| **Requires Operational Control** | The technical prerequisite exists, but the obligation is only satisfied by a human/organizational process (a policy, a signed agreement, a review cadence) that this codebase cannot itself provide. |
| **Requires Legal Review** | Statutory interpretation or a compliance conclusion here needs a qualified lawyer, not an engineer's judgment. |
| **Not Yet Implemented** | No control exists yet. |

**Provenance note, stated once here rather than repeated per row**: every `legalReference`/`sourceReference` pair below is taken verbatim from `packages/database/prisma/seed.ts`, where it was recorded at the time the corresponding rule was authored (2026-08-18). The primary source used was a plain-text extraction of Act No. 11 of 2007 (via mwakili.com), cross-checked against secondary legal-summary sources (a Studocu summary, a LinkedIn legal analysis, and several Kenyan law-firm blog posts) that were consistent with each other and with general knowledge of the statute. **None of this was verified against the primary Kenya Law Reports text directly.** Treat every row's "Section" citation as a strong, well-corroborated draft, not a confirmed legal citation — this is the single most important caveat in this entire document, and it was already stated in the code before this document existed (`docs/architecture.md` §13, `packages/database/prisma/seed.ts` lines 160–171).

**What the deterministic engine deliberately does NOT do**: attempt statutory arithmetic or legal judgment via the AI orchestration service. `apps/ai`'s contract-audit agent is explicitly prompted not to re-derive or contradict this engine's output (`apps/ai/app/orchestration/prompts/contract_audit_v1.py`) and its findings use a different severity vocabulary (`INFO`/`ADVISORY`/`CONCERN`, not `PASS`/`WARNING`/`FAIL`) specifically so the two can never be confused in the UI (`ContractAiAuditPanel.tsx`) or the API response shape. This is a structural control, not a policy — see `docs/architecture.md` §15.

## 2. Data Protection Act 2019 (Kenya) — architecture mapping

The DPA 2019 imposes obligations on **data controllers and processors**; Nexa Workforce Solutions Ltd (or its client organizations, depending on the actual contractual relationship — **Requires Legal Review** to determine who is controller vs. processor for each tenant) is the entity with the legal obligation, not this codebase. What follows maps *technical controls that exist* to the *areas* the Act covers — it is not a compliance certification.

| DPA 2019 Area | Technical Control | Implementation Location | Status | Distinguishing note |
|---|---|---|---|---|
| **Data security / integrity & confidentiality** | Argon2id password hashing; JWT access/refresh with rotation and reuse-detection; PostgreSQL RLS as the tenant-isolation backstop; httpOnly, `secure`-in-production cookies (never `localStorage`); TLS is a deployment-environment responsibility, not baked into this app layer | `packages/auth/src/password.ts`, `refresh-token.ts`; `packages/database/prisma/rls/*.sql`; `apps/web/lib/auth/cookies.ts` | Implemented (technical controls) / Requires Operational Control (TLS termination, key management) | A strong technical control is not the same as a documented ISMS or a completed risk assessment |
| **Access controls** | RBAC with per-request, DB-fresh permission resolution (never trusting JWT-embedded permissions); every guard chain independently re-verified per request | `apps/api/src/tenancy/tenant-context.guard.ts`, `apps/api/src/authorization/permissions.guard.ts` | Implemented | — |
| **Data minimization** | AI audit logging stores only SHA-256 hashes of prompts/outputs, never raw content (`AIAuditLog.inputRef`/`outputRef`); contract/employee data sent to Claude is the minimum needed for the specific agent task, not a full record dump | `apps/ai/app/services/audit_repository.py`; `apps/ai/app/orchestration/prompts/*.py` | Partially Implemented | The AI *audit trail* minimizes what's retained; the AI *request itself* still sends real contract particulars to a third-party processor — see cross-border note below |
| **Purpose limitation** | Statutory payroll data is used only for payroll calculation/reporting; AI agents receive only the fields their specific task needs (e.g. BPO QA never sees payroll data) | Module boundaries throughout `apps/api` | Partially Implemented | No formal, documented purpose-limitation policy exists outside of what the code structurally enforces |
| **Retention** | No automated retention/deletion policy exists anywhere in the schema — `AuthenticationAuditEvent`, `AIAuditLog`, `ComplianceEvaluation`, sessions, and refresh tokens all accumulate indefinitely today | — | Not Yet Implemented | This is a real, material gap, not an oversight to gloss over |
| **Data-subject rights** (access, correction, erasure, objection) | No API endpoint exists for a data subject (an `Employee` or `User`) to request their own data, request correction, or request erasure | — | Not Yet Implemented | RLS ensures data is *isolated per tenant*, which is necessary but not sufficient for data-subject rights, which are about the individual, not the organization |
| **Breach notification** | Structured audit events exist (`AuthenticationAuditEvent`, `AIAuditLog`) that *could* feed a breach-detection process, but no alerting, no incident-response runbook, and no notification workflow exist in this codebase | `docs/production-readiness.md` §Observability notes extension points (Sentry, OTel) but none are wired up | Not Yet Implemented | A breach notification *obligation* is entirely organizational; this repo provides raw material for detection, not the process itself |
| **Controller/processor responsibilities** | Not modeled at all — the platform does not currently distinguish "Nexa acting as processor for a client" from "Nexa acting as controller for its own HR data" anywhere in code or contract | — | Requires Legal Review | This determination affects which DPA obligations attach to which party and should be settled contractually, not inferred from the schema |
| **Cross-border processing** | Contract/employee data used in an AI contract audit or BPO QA review is sent to Anthropic's API (a US-based processor) over TLS; `apps/ai`'s system prompts instruct the model not to fabricate data, but the underlying data transfer itself is real | `apps/ai/app/orchestration/client.py` (the actual API call) | Requires Legal Review | Kenya's DPA 2019 restricts cross-border transfers to jurisdictions with adequate safeguards or under specific conditions (consent, contractual clauses) — whether Anthropic's terms/DPA satisfy this for a given client's data is a legal determination, not a code question. **This is the second-highest-risk item in this document.** |
| **Auditability** | `AIAuditLog` and `AuthenticationAuditEvent` provide a real, queryable audit trail for AI activity and auth events specifically; there is no general-purpose "who accessed which employee record when" audit log for ordinary CRUD reads | `packages/database/prisma/schema.prisma` (`AIAuditLog`, `AuthenticationAuditEvent`) | Partially Implemented | Read access to sensitive records (e.g. viewing an employee's payroll history) is not itself logged today |

## 3. Statutory payroll compliance matrix

All four statutory areas share the same architecture: a versioned `StatutoryRuleVersion` row (with `effectiveFrom`/`effectiveTo`, `taxYear`, and a `sourceReference` citation) feeds `packages/payroll-engine`, a pure function with no I/O, no Prisma, and no AI — see `docs/architecture.md` §13's "Payroll engine boundary." **Every rate/threshold below was researched on 2026-08-18 and is explicitly marked in `packages/database/prisma/seed.ts` (lines 160-171, and per-row) as corroborated-but-not-verified against a primary KRA/NSSF/SHA/Gazette source.**

| Statutory Area | Calculation Source (as seeded) | Reference Data Location | Calculation Engine | Database Record | Payroll Output | Test Coverage | Update Mechanism | Status |
|---|---|---|---|---|---|---|---|---|
| **PAYE** | 5 progressive bands (10%/25%/30%/32.5%/35%), personal relief KES 2,400/month — cited to Finance Act 2023, corroborated via smarthr.co.ke and payecalculator.co.ke; KRA's own public notice page returned a stale pre-2023 table when checked directly | `StatutoryRuleVersion` (`ruleType: PAYE`), `seed.ts:184-201` | `packages/payroll-engine/src/paye.ts` (pure, band-based, decimal.js) | `PayrollRecord.payeAmount`, `.payeBeforeRelief`, `.personalRelief` | `PayrollRunSummaryReport.paye`; gross-to-net calculator preview | `packages/payroll-engine`'s 108-test suite (executed, passing — see `docs/architecture.md` §13) | New `StatutoryRuleVersion` row with a new `effectiveFrom`; old row's `effectiveTo` set; no code change needed | Implemented, source **Requires Legal Review** |
| **NSSF** | Two-tier (Tier I: 6% up to KES 9,000; Tier II: 6% from 9,000–108,000), Feb 2026 step — cited to NSSF Act 2013 phased schedule via CM Advocates LLP; no specific 2026 Board gazette notice number located | `StatutoryRuleVersion` (`ruleType: NSSF`), `seed.ts:203-233` | `packages/payroll-engine/src/nssf.ts` | `PayrollRecord.nssfEmployeeAmount`, `.nssfEmployerAmount` | Same report/calculator paths as above | Same suite | Same mechanism | Implemented, source **Requires Legal Review** |

| **Affordable Housing Levy** | 1.5% employee + 1.5% employer, no cap modeled — cited to Affordable Housing Act 2024; effective date (2024-03-19) is approximate | `StatutoryRuleVersion` (`ruleType: HOUSING_LEVY`), `seed.ts:248-259` | `packages/payroll-engine/src/housing-levy.ts` | `PayrollRecord.housingLevyEmployeeAmount`, `.housingLevyEmployerAmount` | Same | Same suite | Same mechanism | Implemented, source **Requires Legal Review** |

**Responsible review**: no named individual or role currently owns statutory-rate review in this organization (there is no "compliance officer" role or scheduled review cadence in the seed data or documentation) — this is a **Requires Operational Control** gap across all four rows: the *mechanism* to update rates safely exists; the *organizational process* to actually notice a rate change and act on it does not.

### 3a. Statutory data governance (brief §40)

The schema already models exactly the fields the brief asks for, on `StatutoryRuleVersion`:

| Field the brief asks for | Schema field | Present? |
|---|---|---|
| `effective_from` | `effectiveFrom` (`@db.Date`, required) | Yes |
| `effective_to` | `effectiveTo` (`@db.Date`, nullable — open-ended until superseded) | Yes |
| `jurisdiction` | `jurisdictionId` → `StatutoryJurisdiction.countryCode` (currently only `KE` seeded) | Yes |
| `statutory_source` | `sourceReference` (free-text citation, populated for every seeded row — see §1/§3 above) | Yes |
| `version` | Not a discrete field — `taxYear` + `effectiveFrom` together serve as the natural version key (`@@unique([jurisdictionId, ruleType, effectiveFrom])`) | Partially — no single `version` string column |
| `review_status` | Not modeled | No |

**Historical reproducibility (brief §40's core requirement) is genuinely implemented**, not aspirational: `PayrollRunStatutoryRule` pins the exact `StatutoryRuleVersion` id used for PAYE/NSSF/SHIF/Housing Levy at the moment a payroll run is calculated (`docs/architecture.md` §13's "Statutory rule pinning"). A future rate change creates a *new* `StatutoryRuleVersion` row; it never mutates an existing one, and never touches `PayrollRunStatutoryRule` rows from past runs. Re-running a report against a historical `PayrollRun` will always reproduce the figures using the rates that were actually pinned at calculation time — this was verified by code inspection of the pinning mechanism (`payroll.service.ts`'s `calculate()`, which upserts `PayrollRunStatutoryRule` inside the same transaction that computes records) and is a structural guarantee, not a policy promise.

**Gap**: there is no `review_status` field and no scheduled-review tooling — a rate could silently go stale (its real-world effective period ending) with nothing in the system flagging it. `Not Yet Implemented`.

## 4. Legal source verification summary

Every legal citation in this document and in the underlying code (`compliance-validator.ts`, `seed.ts`) was sourced by secondary-source web research performed on **2026-08-18**, cross-checked across multiple independently-authored sources that agreed with each other. **None of it was verified against Kenya Law Reports, the KRA's own current gazette notices, the NSSF Board's gazette notice, or the Social Health Authority's primary publications.** KRA's own public notice page specifically returned a stale (pre-2023) table when checked directly during this research, which is itself a signal that automated/AI-assisted legal research cannot substitute for a primary-source check.

**Before any of this drives a real client's live payroll or contract compliance decisions, a qualified Kenyan employment/tax lawyer or licensed payroll professional must independently verify**:
1. Every Employment Act 2007 section citation in §1's matrix.
2. Every PAYE/NSSF/SHIF/Housing Levy rate, band, and effective date in §3's matrix, against KRA, NSSF, and SHA's current official publications.
3. The controller/processor determination and cross-border transfer basis in §2.

This document is an engineering readiness matrix. It is not, and does not substitute for, legal advice.
